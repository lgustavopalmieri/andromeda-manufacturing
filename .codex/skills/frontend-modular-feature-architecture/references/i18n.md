# Internationalization (i18n)

> Reference for the `frontend-modular-feature-architecture` skill. Reference code:
> `src/i18n.ts`, `src/stores/locale.store.ts`, and `src/features/sign-up/i18n/**`. The app
> uses **react-i18next**; each feature owns a **typed** translation namespace. Supported
> locales today: **`en`** (fallback), **`de`**, **`da`**.

## 1. Core concept

Copy is **not** a loose bag of strings. Each feature declares a **typed contract** for its
translations (`interface.ts`), provides **one file per locale** implementing that contract,
and registers itself as an **i18next namespace** named after the feature. Components read
copy with `useTranslation("<feature>")`; the Zod schema reads validation messages through a
`t` function so **validation is localized too** (see `references/feature-slice.md` §2/§4).

Namespaces in use: `layout` (the app shell) and `sign-up` (the reference feature). New
features add their own namespace.

## 2. The feature's `i18n/` folder

```
features/sign-up/i18n/
├── interface.ts       # SignUpTranslation — the shape every locale must satisfy
├── sign-up.en.ts      # signUpEn: SignUpTranslation  (English — the reference)
├── sign-up.de.ts      # signUpDe: SignUpTranslation  (German)
├── sign-up.da.ts      # signUpDa: SignUpTranslation  (Danish)
└── sign-up.i18n.test.ts   # structural integrity across locales (references/testing.md)
```

**`interface.ts` — the contract.** A nested interface grouping keys by area (`hero`,
`form`, `errors`, `success`). Grouping mirrors how components consume it (`t("form.submit")`,
`t("errors.slug_format")`).

```ts
// i18n/interface.ts — reference example (trimmed)
export interface SignUpTranslation {
  hero: { heading: string; subtitle: string };
  form: {
    fieldset_account: string;
    fieldset_owner: string;
    account_name_label: string;
    account_name_placeholder: string;
    slug_label: string;
    slug_placeholder: string;
    /* …every label & placeholder… */
    submit: string;
    submitting: string;
  };
  errors: {
    account_name_required: string;
    slug_required: string;
    slug_format: string;
    owner_email_required: string;
    owner_email_invalid: string; /* … */
  };
  success: string;
}
```

**The locale files — typed implementations.** Each exports a `const` **typed with the
interface**, so a missing or misspelled key is a compile error.

```ts
// i18n/sign-up.en.ts — reference example (trimmed)
import { SignUpTranslation } from "./interface";

export const signUpEn: SignUpTranslation = {
  hero: {
    heading: "Create Your Account",
    subtitle: "Set up your workspace and owner profile to get started.",
  },
  form: {
    fieldset_account: "Account",
    account_name_label: "Account Name",
    account_name_placeholder: "Acme Corp",
    /* … */
    submit: "Create Account",
    submitting: "Creating Account…",
  },
  errors: {
    slug_format: "Slug may only contain lowercase letters, numbers, and hyphens.",
    /* … */
  },
  success: "Account created. Check your email to complete registration.",
};
```

Copy rules (enforced by tests and the a11y conventions):

- **Title Case** for labels, headings, and button text ("Create Account", not "Create
  account").
- **Loading labels** end with a real ellipsis character `…` ("Creating Account…"), never
  three dots.
- **Error messages include a next step** where relevant, not just the problem.
- The English file is the **reference**: other locales must have exactly the same keys
  (the i18n test asserts this).

## 3. Registering the namespace — `src/i18n.ts`

`src/i18n.ts` initializes i18next once and registers every feature/layout namespace under
each locale. Adding a feature means importing its locale files and adding them here.

```ts
// src/i18n.ts — reference example (trimmed)
import i18n from "i18next";
import { initReactI18next } from "react-i18next";
import LanguageDetector from "i18next-browser-languagedetector";
import { signUpEn } from "./features/sign-up/i18n/sign-up.en";
import { signUpDe } from "./features/sign-up/i18n/sign-up.de";
import { signUpDa } from "./features/sign-up/i18n/sign-up.da";
// …layout namespace imports…

i18n
  .use(LanguageDetector)
  .use(initReactI18next)
  .init({
    resources: {
      en: { layout: layoutEn, "sign-up": signUpEn },
      de: { layout: layoutDe, "sign-up": signUpDe },
      da: { layout: layoutDa, "sign-up": signUpDa },
    },
    fallbackLng: "en",
    interpolation: { escapeValue: false },
    detection: {
      order: ["localStorage", "navigator"],
      lookupLocalStorage: "andromeda-locale",
      caches: [],
    },
  });

export default i18n;
```

- **The namespace key is the feature name** (`"sign-up"`). Components use it:
  `useTranslation("sign-up")`.
- **Language detection:** `localStorage` (key `andromeda-locale`) first, then the browser's
  `navigator`. `fallbackLng: "en"`.
- `main.tsx` imports `./i18n` for its side effect so init runs before the app mounts.

## 4. The locale store — switching language

`stores/locale.store.ts` is the user-facing switch. It uses Zustand's `persist` middleware
(same `andromeda-locale` key) and keeps i18next in sync on both `setLocale` and rehydrate.

```ts
// stores/locale.store.ts (trimmed)
export const LOCALE = { EN: "en", DE: "de", DA: "da" } as const;
export type Locale = (typeof LOCALE)[keyof typeof LOCALE];

export const useLocaleStore = create<LocaleState>()(
  persist(
    (set) => ({
      locale: LOCALE.EN,
      setLocale: (locale) => {
        i18n.changeLanguage(locale);
        set({ locale });
      },
    }),
    {
      name: "andromeda-locale",
      onRehydrateStorage: () => (state) => {
        if (state) i18n.changeLanguage(state.locale);
      },
    },
  ),
);
```

## 5. Localized validation (the schema ↔ i18n link)

Validation messages localize because the schema is a **factory** taking a `t` function, and
the hook rebuilds it when the language changes:

```ts
// in use-<feature>-form.ts
const schema = useMemo(() => {
  const t = i18n.getFixedT(i18n.language, "sign-up"); // pin translator to this namespace + current locale
  return makeSignUpSchema(t);
}, [i18n, i18n.language]);
```

`getFixedT(language, namespace)` returns a translator locked to the active locale and the
feature's namespace; when `i18n.language` changes, `useMemo` rebuilds the schema and new
validation errors come out in the new language. See `references/feature-slice.md` §2/§4.

## 6. How to start (new feature namespace)

1. Create `features/<feature>/i18n/interface.ts` with a `Feature Translation` interface,
   grouped by area (`hero`/`form`/`errors`/…).
2. Add `<feature>.en.ts` (the reference), then `<feature>.de.ts`, `<feature>.da.ts`, each
   `export const … : <Feature>Translation`.
3. Register the namespace in `src/i18n.ts` (import the locale consts, add them under `en`,
   `de`, `da`).
4. Consume with `useTranslation("<feature>")` in components; pass `getFixedT(language,
"<feature>")` into the schema factory in the hook.
5. Add the i18n structural test (`references/testing.md`) so all locales stay in sync.

## 7. Common mistakes (what NOT to do)

- ❌ Hard-coding a literal string in a component or schema. ✅ Every string is a key read
  through `t(...)`.
- ❌ An untyped translation object. ✅ Type each locale file with the feature's
  `interface.ts` so missing keys fail to compile.
- ❌ Locales drifting apart (a key added only to `en`). ✅ The i18n test enforces identical
  key sets and non-empty values across locales.
- ❌ Building the Zod schema outside the hook / not rebuilding on locale change. ✅
  `useMemo` keyed on `i18n.language` + `getFixedT`, so validation re-localizes.
- ❌ Three-dot "..." in loading/placeholder copy. ✅ The `…` ellipsis character.
- ❌ Forgetting to register a new namespace in `src/i18n.ts`. ✅ Add it under every locale.
